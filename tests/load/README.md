# Навантажувальне тестування (k6)

Перевіряє дві нефункціональні вимоги:

- **NFR-3**: система працює без деградації при 200+ одночасних користувачах (менше 1 % помилок, усі перевірки відповідей проходять);
- **NFR-5**: пошук і зміна статусу книги (бронювання, скасування) займають менше 1 с (95-й перцентиль).

## Сценарій

[`library.js`](library.js): 200 віртуальних користувачів (30 с нарощування → 3 хв під навантаженням → 20 с спаду). Кожен проходить сесію читача з паузами 1–4 с між діями:

вхід → сторінка каталогу → каталог на 100 книг (так його вантажив фронтенд до переходу на нескінченну прокрутку; заміри нижче зроблені з цим запитом) → пошук → фільтр за жанром → деталі книги → бронювання → «Мої видачі» → скасування броні.

Перед стартом `setup()` створює бібліотекаря, 20 книг по 100 примірників і по одному читачу на кожного віртуального користувача. Відповідь 409 на бронювання (усі примірники зайняті, ліміт 5 книг) вважається очікуваною бізнес-відповіддю, а не збоєм. Частку таких відповідей показує метрика `reservation_conflicts`.

## Запуск

Потрібні Docker і запущений `docker compose` (БД + бекенд). Код бібліотекаря береться з `.env`.

```bash
CODE=$(grep '^LIBRARIAN_INVITE_CODE=' .env | cut -d= -f2)
docker run --rm -i -v "$PWD/tests/load:/scripts" \
  -e BASE_URL=http://host.docker.internal:5000/api -e LIBRARIAN_CODE=$CODE \
  -e K6_WEB_DASHBOARD=true -e K6_WEB_DASHBOARD_EXPORT=/scripts/results/dashboard.html \
  grafana/k6:2.3.0 run --summary-export /scripts/results/summary.json /scripts/library.js
```

Параметри через `-e`: `VUS` (типово 200), `HOLD` (типово `3m`), `THINK` (множник пауз; `0` вимикає паузи, тобто стрес-тест). У Git Bash на Windows перед командою додайте `MSYS_NO_PATHCONV=1`.

HTML-дашборд з графіками (`results/dashboard.html`) відкривається в браузері. Тека `results/` у git не потрапляє.

### Великий обсяг даних

[`seed-large.sql`](seed-large.sql) додає 50 000 книг, 150 000 примірників, 5 000 читачів і 200 000 записів історії видач. **Тільки для локальної або тестової бази!**

```bash
docker compose exec -T db psql -U postgres -d SimpleLibraryDb < tests/load/seed-large.sql   # ~3–4 хв
docker compose exec -T db psql -U postgres -d SimpleLibraryDb < tests/load/explain.sql      # плани запитів
```

Повернути чисту базу: `docker compose down -v && docker compose up -d`.

## Результати (18.10.2026)

Середовище: ноутбук, Docker Desktop (8 CPU, 8 ГБ RAM), бекенд і PostgreSQL 16 у контейнерах, k6 на тій самій машині.

| 200 користувачів, 3 хв | ~60 книг | 50 000 книг, без індексів | 50 000 книг, з індексами |
|---|---|---|---|
| Пошук і фільтр, p95 (NFR-5) | 25 мс ✅ | **8,95 с** ❌ | **54 мс** ✅ |
| Бронювання та скасування, p95 (NFR-5) | 44 мс ✅ | **2,06 с** ❌ | **62 мс** ✅ |
| Усі запити, p95 | 218 мс | 6,4 с | 223 мс |
| Невдалі запити (NFR-3) | 0 % ✅ | 0,01 % ✅ | 0 % ✅ |
| Запитів за секунду | 95 | 56 | 94 |
| CPU PostgreSQL, середнє | 42 % | 353 % | 45 % |

### Що показав тест

1. **Без індексів NFR-5 не виконується на реалістичних даних.** Пошук генерує `lower("Title" COLLATE "und-x-icu") LIKE '%...%'`, а звичайний B-tree індекс такому шаблону не допомагає, тож кожен запит перебирав усю таблицю (Seq Scan). Під навантаженням це довело PostgreSQL до 760 % CPU.
2. **Рішення:** міграція `AddPerformanceIndexes` додає 7 індексів. Найважливіші з них — триграмні GIN-індекси `pg_trgm` саме на виразі з пошуку. Час виконання окремих запитів у базі (`explain.sql`):

   | Запит | Без індексів | З індексами |
   |---|---|---|
   | Пошук: кількість | 117 мс | 11,6 мс |
   | Пошук: сторінка | 107 мс | 47 мс |
   | Фільтр за жанром | 46 мс | 0,5 мс |
   | Каталог, сторінка 3 | 17 мс | 0,7 мс |
   | Активні видачі та боржники | 23 мс | 3,3 мс |

3. **Найповільніша операція — вхід (~200 мс).** Це очікувано: bcrypt навмисно повільний, бо так захищає паролі. Саме вхід визначає загальний p95.
4. **Пул з'єднань.** Під навантаженням без індексів бекенд тримав усі 100 з'єднань із PostgreSQL. Це стандартний `Max Pool Size` у Npgsql, і він дорівнює `max_connections` бази, тож навіть адміністратор не міг підключитися. Рекомендація: задати `Maximum Pool Size` меншим за `max_connections` (наприклад, 50).
5. **Обмеження тесту:** k6 і застосунок працюють на одній машині, тому абсолютні числа для хмарного розгортання (Cloud Run + Neon) будуть іншими. Порівняння «до / після» при цьому коректне.
